## 0. Why this exists (the problem being fixed)

The docs only advance when CC runs a blueprint. Chat-only sessions (design, red-teaming, sequencing decisions) produce real state changes that land in no durable home. Across chat-to-chat transitions, these deltas are carried in prose handoffs written from chat-side memory, and they drift. A worked failure: a 2026-06-14 chat opened on a handoff describing a "static-game blueprint, CC returned green, seasonal-forage next, p_female / kcal energy-balance system, 430 tests" state — **none of which exists in the committed repo** (frontier is Phase 1 Stage 1c, complete 2026-06-13). That phantom state was nearly used as the basis for new design work.

The fix is two artifacts with a controlled relationship to the eleven charter homes:
- a **derived fact-file** — a read-optimised projection (cache) of the homes, so a fresh chat reconstructs committed state without trusting memory;
- a **pending-delta buffer** — a write-ahead log of chat-side decisions CC has not yet reconciled, so uncommitted state is *visibly pending* rather than laundered into apparent fact.

**Governance note (binding):** per DOCS_CHARTER §1.3 (closed set), neither artifact may become a twelfth/thirteenth top-level home in `docs/`. They live in a new `context/` directory, explicitly **non-canonical**. On any conflict, the eleven homes win. The fact-file is a *projection* of canon (allowed to restate facts only because it defers to them); the pending-delta buffer is a *buffer*, never canon. No charter amendment is required because no new `docs/` home is created — but **add a one-line pointer in `docs/INDEX.md`** noting that `context/` exists and is derived/non-authoritative.

### Task 3 — Create `context/PENDING_CC.md` (the pending-delta buffer)
Append-only, strict format. One block per entry:
```
- [PENDING] <date> | <type> | <one-line statement> | home-target: <which doc this drains into>
```
where `<type> ∈ {decision, deferral, hypothesis-sketch, sequencing, correction, flag}`.
Seed it with this session's deltas (Task 5).
Header states: append-only; each entry is PENDING until CC drains it into its home-target and marks it `[DRAINED <date>]` (struck-through, not deleted — append-only ledger).

### Task 4 — Extend CLAUDE.md with two standing rules
Append to the standing-rules block (these are rules 14 and 15):

> **14. Drain the pending-delta buffer on every run (added 2026-06-14).** At the start of any blueprint/directive execution, read `context/PENDING_CC.md`. For each `[PENDING]` entry, reconcile it into its home-target: if it agrees with the home, mark `[DRAINED <date>]`; if it **conflicts** with a home, do NOT silently resolve — surface it to the supervisor (charter §1 conflict-surfacing) and leave it `[PENDING]` with a `[CONFLICT]` tag.
