# START HERE — SiC Games audit package, 2026-10-26

**What this folder is.** A dated audit package for an extensive, in-depth review of the SiC Games model. It states the
model's state on one date, explains where everything is, and points to the evidence. It was prepared by the coding
agent at the supervisor's request (Dr. Shurik Yatom). **Snapshot:** branch `r106/add105-malthus-churn` on
`github.com/ShuraBura/SiC-Games`, at the commit that added this folder (`git log -1 -- audit/2026-10-26`). The model's
canon is the R-106 Addendum-113 canon. Everything here describes that commit; later commits can change it.

**What this folder is NOT.** It is not the authoritative home of any fact. The project keeps one home for each kind of
fact (`docs/INDEX.md`); this package is a dated view of those homes, with pointers. Where this package and a home
disagree, report it as a finding — and the home, or the code, is what ran.

## The project in one page

**What the model is.** An agent-based model (Python 3.14, Mesa) of emergent social evolution. Agents live on
climate-generated terrain worlds (100 × 100 cells; 1 cell ≈ 100 km²; 1 step = 1 month). They forage and hunt in kcal,
store food, form pair bonds, families, bands, villages and connubia, and develop status, material wealth, lineages and
an elite layer. Demography is explicit: a Siler mortality schedule modulated by terrain risk, density disease and
nutrition; energetic fertility; provisioning of children by mothers and fathers. Every mechanism is a flag (125 in
all); the canonical run switches on 98 of them.

**History.**
- **Phase 0 (June 2026):** two strategies, C (cooperative) and Si (individualist), on a Sugarscape grid; question
  H1(ii), which is more resilient to shocks (RESULTS R-1). **Historical.** The C/Si question is not the current work;
  the many `stage*.py` modules in the package belong to this phase.
- **Phase 1 (June–August 2026):** terrain and resource ecology, then demography, Carbon status, climate, bands,
  settlements, agriculture, the elite layer (RESULTS R-2 … R-98).
- **The R-106 calibration arc (July 30 – October 2026):** make the model reproduce the ethnographic record on three
  canonical worlds before any secular-cycles layer (RESULTS R-106 and its Addenda 1–114). The supervisor's overarching
  goal: population must expand and spread while food lasts, and contract on external shocks (Malthusian pressure).

**The three canonical worlds:** temperate (coastal terrain, temperate climate), savanna (coastal, savanna), montane
(mountainous, savanna). **The canonical run** is `config/runs/full_campaign.toml`, executed by
`sic_games/outputs/substrate_run/run_campaign.py`.

**State in four lines** (details in `01_CURRENT_STATE.md` and `02_BENCHMARKS.md`):
1. All banded markers of the marker table pass on all three worlds, except two unresolved on temperate.
2. The demography monitor does not fully pass: fertility (TFR) is below the forager band on every world (it was in
   band before the last two adoptions), and mortality at ages 5–15 has never been in band.
3. The population does not disperse to its food (the spatial paradox flag is TRUE on every run).
4. Every result rests on one planet (world/climate seed 0) with three demographic seeds.

## How to treat the evidence

- **Order of precedence:** code > `config/runs/full_campaign.toml` (what the canonical run executes) > the generated
  `config/*.toml` > `docs/` > this package.
- **RESULTS.md is append-only.** A finding is corrected by a LATER entry, never by an edit. Before you rely on an
  entry, check `docs/RESULTS_INDEX.md` and search for later entries that name it. Several conclusions were later
  retracted or refuted (a list is in `docs/DEAD_ENDS.md` DE-23).
- **"Bit-exact when off".** Every mechanism is a flag whose class default is OFF, so historical runs reproduce exactly.
  The canonical stack is separate: it switches on every built mechanism except a recorded `_skip` set.
- **Absolute values are valid only on the canon where they were measured** (`docs/MARKER_MATRIX.md` rule 5).

## How to classify a finding (carried over from the June audit guide)

1. **INCONSISTENCY** — two parts of the repo contradict each other: spec vs code, doc vs run file, a value vs its cited
   source, a conclusion vs its own evidence. The most useful class.
2. **UNSUPPORTED CLAIM** — a value, mechanism or conclusion with no traceable backing.
3. **DESIGN PREFERENCE** — internally consistent, but you would do it differently. Low priority; label it as such.

**Suggested mode:** read and run freely; write nothing in the tracked tree; put your report and scratch outputs outside
the repository. A failing test or a bug is a finding to document, not to fix.
